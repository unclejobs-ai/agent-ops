# Claude Perfect Guide

> 잘 쓰면 에이전트, 못 쓰면 비싼 챗봇  
> Claude Code · Cowork · Projects · Chat를 제대로 쓰는 가장 실전적인 방법

이 문서는 Claude를 설명하는 문서가 아니다.  
**Claude와 함께 일하는 방식을 설계하는 문서**다.

---

# 시작하며

많은 사람이 Claude를 똑똑한 채팅창으로 쓴다.
질문하고, 답을 받고, 만족하거나 실망하고 끝낸다.

그 방식도 틀린 건 아니다.
그런데 거기서 멈추면 Claude를 반밖에 못 쓴다.

진짜 차이는 그다음부터 난다.
누군가는 질문만 한다.
누군가는 일을 맡긴다.
그리고 더 잘 쓰는 사람은 한 번 더 나아간다.

- 어디에 맡길지 고르고
- 무엇만 보게 할지 정하고
- 어디까지 하게 할지 선을 긋고
- 끝난 뒤 어떻게 검수할지까지 정한다

그 차이가 생산성 차이이고, 결과물 차이이고, 결국 실력 차이다.

# 1. Claude를 챗봇처럼 쓰면 왜 손해인가

## Claude는 하나가 아니다

Claude는 하나의 제품이라기보다 여러 작업면으로 나뉜 작업 시스템에 가깝다.
같은 모델이라도 어디에서 쓰느냐에 따라 잘하는 일이 달라진다.

- **Chat**은 질문하고 정리하는 데 강하다
- **Projects**는 같은 배경을 오래 들고 가는 데 강하다
- **Cowork**는 문서와 파일 중심 작업을 맡기기에 좋다
- **Claude Code**는 구현, 수정, 테스트, 검증에 강하다

같은 두뇌라도 앉혀 놓는 자리가 다르면 결과가 달라진다.
이걸 놓치면 “Claude가 별로다”가 아니라 **작업대 선택이 틀린 경우**가 많다.

## 왜 어떤 사람은 10배 빨라지고, 어떤 사람은 토큰만 태울까

문제는 대개 모델이 아니다.
대부분의 문제는 아래 다섯 군데에서 터진다.

1. 작업면을 잘못 고른다
2. 범위를 안 정하고 맡긴다
3. 컨텍스트를 무작정 길게 넣는다
4. 검증 루프 없이 결과만 받는다
5. 권한과 보안 경계를 너무 늦게 생각한다

Claude를 잘 쓰는 사람은 말을 화려하게 하는 사람이 아니다.
**작업장을 잘 만드는 사람**이다.

# 2. 5분 만에 이해하는 Claude 작업면

## 한 장 비교

| 작업면 | 가장 잘하는 일 | 약한 일 | 잘 맞는 사람 |
|---|---|---|---|
| Chat | 질문, 요약, 초안, 생각 정리 | 장기 운영, 복잡한 실행 | 모두 |
| Projects | 같은 배경 유지, 문맥 누적 | 직접 실행 | PM, 연구자, 창업가 |
| Cowork | 회의록 정리, 브리프, 자료 정리, 비개발 업무 위임 | 깊은 코드 수정 | 운영자, 마케터, 비개발 실무자 |
| Claude Code | 코드 탐색, 수정, 테스트, 리팩터링, 검증 | 광범위한 문서 업무 | 개발자 |

## 가장 쉬운 선택법

### Chat에 올릴 일
- 생각 정리
- 질문 재정리
- 빠른 초안
- 짧은 요약

### Projects에 올릴 일
- 장기 프로젝트 배경 유지
- 공통 전제 누적
- 매번 다시 설명하기 싫은 맥락

### Cowork에 올릴 일
- 회의록 → 브리프
- 자료 정리
- 문서 초안
- 파일 기반 지식 업무

### Claude Code에 올릴 일
- 버그 수정
- 리팩터링
- 테스트 작성
- 구현과 검증이 같이 필요한 일

## 좋은 첫 과제와 나쁜 첫 과제

처음에는 **작고, 되돌리기 쉽고, 끝이 보이는 일**부터 맡기는 편이 좋다.

### 좋은 첫 과제
- 보고서를 5문장 요약과 3개 질문으로 정리하기
- 회의 메모를 주간 브리프로 바꾸기
- 버그 수정 전에 원인 가설과 수정 계획만 먼저 세우기
- 참고 자료를 템플릿 구조에 맞게 정리하기

### 나쁜 첫 과제
- 외부 도구를 첫날 전부 붙이기
- 범위 없이 “서비스 전체 개선해줘”라고 던지기
- 승인선 없이 메일 발송, 삭제, 정산 입력을 자동화하기
- 예시 없이 “우리 톤으로 다 알아서 해줘”라고 하기

처음엔 큰일을 빨리 맡기는 것보다 작은 일을 안전하게 맡기는 쪽이 낫다.

# 3. 좋은 요청은 어떻게 생겼나

좋은 결과는 좋은 모델에서만 나오지 않는다.
대부분은 **좋은 작업 경계**에서 나온다.

## 좋은 요청 vs 나쁜 요청

### 예시 1. 버그 수정

**나쁜 요청**  
로그인 버그 고쳐줘.

**좋은 요청**  
auth 관련 파일만 읽고, env와 배포 설정은 건드리지 말고, 먼저 원인 가설을 세운 뒤 가장 작은 수정으로 해결해 줘. 끝나면 바뀐 파일과 검증 결과를 같이 남겨줘.

### 예시 2. 주간 브리프

**나쁜 요청**  
이번 주 시장 업데이트 만들어줘.

**좋은 요청**  
이 메모와 링크를 읽고 이번 주에 바뀐 점만 요약해 줘. 우리에게 왜 중요한지 설명하고, 마지막에는 액션 아이템 3개만 제안해 줘.

## 좋은 요청의 다섯 요소

좋은 요청은 대체로 아래 다섯 가지 중 최소 세 가지를 갖고 있다.

1. 범위
2. 금지선
3. 작업 순서
4. 출력 형식
5. 검증 기준

좋은 요청은 Claude를 더 똑똑하게 만드는 게 아니다.
**덜 흔들리게 만드는 것**에 가깝다.

## 왜 긴 프롬프트보다 경계가 중요한가

AI에게 일을 맡길 때 가장 흔한 실수는 “자세히 말하면 더 잘하겠지”라고 믿는 것이다.
문제는 길이가 아니라 구조다.

범위를 안 정하고 맡기면 결과는 대개 넓고 흐려진다.
반대로 선명한 경계가 있으면 결과는 짧아도 또렷해진다.

# 4. Claude Code를 제대로 쓰는 핵심 루프

Claude Code의 핵심은 답변이 아니라 루프다.

## 탐색 → 계획 → 실행 → 검증

### 1) 탐색
관련 파일과 원인을 좁힌다.

### 2) 계획
무엇을 바꿀지, 왜 바꿀지 정리한다.

### 3) 실행
가장 작은 수정부터 적용한다.

### 4) 검증
테스트와 실제 동작 기준으로 확인한다.

많은 초보자가 계획과 검증을 건너뛴다.
그래서 처음엔 잘하는 것 같다가도, 뒤로 갈수록 왜 바꿨는지 모르겠고 믿기도 어려운 결과를 받게 된다.

## 가장 중요한 원칙

> Claude가 스스로 검증할 수 있게 만들어라.

검증 없는 결과는 초안일 뿐이다.

## handoff와 작업 기록

좋은 작업은 끝날 때도 깔끔해야 한다.
다음 사람이 바로 이어받을 수 있도록 아래 네 가지를 남겨야 한다.

1. 지금까지 한 일
2. 아직 안 끝난 일
3. 남은 리스크
4. 다음에 제일 먼저 볼 것

# 5. 컨텍스트 관리가 실력이다

컨텍스트는 많다고 좋은 게 아니다.
너무 많이 넣으면 느려지고, 비싸지고, 초점이 흐려진다.

Claude는 지금 입력한 문장만 읽지 않는다.
이전 대화, 읽은 파일, 규칙 파일, 도구 결과, 방금 만든 출력까지 함께 끌고 간다.

즉 컨텍스트는 메모리가 아니라 **작업 반경**에 가깝다.
줄여야 선명해진다.

## 상시 규칙과 임시 지시 나누기

### 항상 필요한 것
- 프로젝트 기본 규칙
- 금지선
- 핵심 배경
- 반복 작업 원칙

이런 건 `CLAUDE.md`처럼 상시로 두는 게 낫다.

### 가끔 필요하지만 길고 구체적인 것
- 특정 작업 절차
- 반복 템플릿
- 상황별 상세 가이드

이런 건 Skill로 빼는 편이 낫다.

### 문맥을 너무 많이 먹는 것
- 로그 대량 분석
- 탐색량이 큰 조사 작업
- 메인 작업과 별개인 읽기 작업

이런 건 Subagent처럼 별도 문맥에서 처리하고 요약만 가져오는 방식이 유리하다.

## CLAUDE.md / Skill / Subagent / Hook / MCP 구분

| 요소 | 역할 | 비유 |
|---|---|---|
| CLAUDE.md | 항상 읽히는 기본 규칙 | 작업장 운영수칙 |
| Skill | 필요할 때 불러오는 절차 | 업무 매뉴얼 |
| Subagent | 별도 문맥에서 일하는 작업자 | 외부 조사 담당자 |
| Hook | 자동으로 도는 검사 규칙 | 자동 검사기 |
| MCP | 외부 도구와 연결하는 길 | 외부 배선 |

## 비용을 덜 태우는 운영 습관

- 작업을 작게 나눈다
- 관련 파일만 읽힌다
- 상시 규칙과 임시 작업을 나눈다
- 탐색량이 큰 일은 따로 뺀다
- 결과만 남기고 불필요한 문맥은 줄인다

# 6. 자동화, 검수, 보안

자동화의 핵심은 사람을 없애는 게 아니다.
**사람이 꼭 봐야 할 지점을 줄이는 것**이다.

## 자동화 가능한 일과 사람이 꼭 봐야 하는 일

| 작업 | 자동화 가능 | 사람 검수 |
|---|---|---|
| 초안 쓰기 | 높음 | 필요 |
| 요약 | 높음 | 권장 |
| 내부 문서 정리 | 높음 | 권장 |
| 코드 수정 | 중간 | 필요 |
| 테스트 실행 | 높음 | 결과 검토 필요 |
| 외부 발송 | 낮음 | 필수 |
| 삭제/결제/권한 | 매우 낮음 | 필수 |

## 강한 에이전트의 문제는 대답이 아니라 권한이다

AI가 더 많은 일을 할수록 문제의 종류도 바뀐다.
예전에는 틀린 답이 문제였다면, 지금은 틀린 행동이 더 큰 문제가 된다.

- 엉뚱한 파일을 읽는다
- 외부 자료의 지시를 그대로 따른다
- 민감한 정보에 닿는다
- 잘못된 자동화를 반복한다

그래서 강한 가이드는 기능을 자랑하는 문서가 아니라, **권한과 보안 경계를 먼저 설계하는 문서**여야 한다.

## 기본 보안 습관

- 처음부터 권한을 넓게 열지 말 것
- 신뢰되지 않은 자료는 그대로 믿지 말 것
- 외부 발송, 삭제, 배포는 승인선을 둘 것
- 읽기용 작업과 실행용 작업을 분리할 것
- 중요한 작업은 로그와 결과를 남길 것

비개발 업무라고 해서 덜 위험한 것도 아니다.
파일과 브라우저를 함께 다루는 작업은 오히려 위험 반경이 넓을 수 있다.

# 7. 역할별 플레이북

## 개발자

개발자에게 Claude의 가장 큰 가치는 “코드 잘 써주는 AI”보다 **코드 작업 전체를 덜 끊기게 만드는 것**에 있다.

### 잘 맞는 작업
- 버그 재현과 원인 가설 정리
- 작은 범위의 안전한 수정
- 테스트 작성
- 리팩터링 계획 수립
- 레거시 코드베이스 온보딩
- PR 리뷰 초안

### 바로 쓸 수 있는 문장
- 이 버그의 재현 경로를 먼저 정리하고, 관련 파일만 좁혀줘.
- 수정 전에 원인 가설 2개와 가장 가능성 높은 원인을 먼저 말해줘.
- 구현보다 먼저 테스트 관점에서 어떤 회귀가 생길지 봐줘.

## PM / 기획자

PM에게 Claude는 아이디어 생성기보다 **배경을 유지하면서 문서를 빠르게 구조화하는 파트너**에 가깝다.

### 잘 맞는 작업
- 회의록 정리
- PRD 초안 작성
- 요구사항 비교표 생성
- 사용자 피드백 묶음 정리
- 기능 우선순위 논리 정리

### 바로 쓸 수 있는 문장
- 이 회의 메모를 읽고 결정사항, 미결사항, 액션 아이템으로 나눠줘.
- 이 기능 요청을 사용자 문제, 비즈니스 가치, 구현 리스크 기준으로 정리해줘.
- 이 PRD 초안을 더 짧고 명확하게 다듬되, 애매한 요구사항은 따로 표시해줘.

## 마케터

마케터에게 Claude는 카피 생성기보다 **자료를 압축하고 메시지를 날카롭게 만드는 편집 파트너**에 가깝다.

### 잘 맞는 작업
- 캠페인 브리프 초안
- 경쟁사 카피 비교
- 랜딩페이지 메시지 구조화
- 광고 훅 정리
- 긴 글의 톤 보정

### 바로 쓸 수 있는 문장
- 이 카피를 더 짧고 세게 만들되, 과장 없이 신뢰감 있게 다듬어줘.
- 이 세 가지 메시지 중 전환 가능성이 높은 축을 비교해줘.
- 고객이 이해하기 어려운 표현은 쉬운 문장으로 바꿔줘.

## 1인 창업가

1인 창업가에게 Claude는 보조 도구가 아니라 **생각, 문서, 구현 사이를 연결하는 멀티툴**에 가깝다.

### 잘 맞는 작업
- 아이디어 정리
- 시장 브리프 요약
- 제품 카피 초안
- 사용자 피드백 정리
- MVP 수정 지원

### 바로 쓸 수 있는 문장
- 이 시장 메모를 읽고 지금 당장 중요한 변화만 골라줘.
- 이 랜딩페이지 메시지를 더 명확하게 만들고, 고객이 헷갈릴 표현은 표시해줘.
- 이 기능은 정말 지금 만들어야 하는지, 가치와 복잡도 기준으로 따져줘.

## 운영 / 리서치 담당자

운영/리서치 담당자에게 Claude는 검색 도구가 아니라 **자료를 읽고 구조화해서 의사결정 가능한 결과물로 바꾸는 도구**에 가깝다.

### 잘 맞는 작업
- 주간 브리프
- 시장 조사 요약
- 커뮤니티 반응 정리
- 긴 문서 압축
- 이슈 분류

### 바로 쓸 수 있는 문장
- 이 자료를 읽고 사실, 해석, 제안으로 나눠줘.
- 지난주와 비교해 새로 바뀐 점만 정리해줘.
- 출처와 날짜를 반드시 붙여서 요약해줘.

## 공통 원칙

직무가 달라도 원리는 같다.
Claude를 잘 쓰는 사람은 더 멋지게 요청하는 사람이 아니라, **작업의 범위, 기준, 검수선을 먼저 정하는 사람**이다.

# 8. 비교로 끝내는 이해

## Claude Code vs Chat형 AI vs IDE 보조도구

| 비교축 | Chat형 AI | IDE 보조도구 | Claude Code |
|---|---|---|---|
| 질문 응답 | 강함 | 약함 | 보통 |
| 프로젝트 전체 탐색 | 약함 | 보통 | 강함 |
| 셸/명령 실행 | 거의 없음 | 제한적 | 강함 |
| 검증 루프 | 약함 | 보통 | 강함 |
| 큰 작업 위임 | 약함 | 보통 | 강함 |
| 장기 운영 구조 | 약함 | 보통 | 강함 |

Claude Code의 진짜 경쟁력은 코드 제안 자체보다 **작업 전체를 맡길 수 있는가**에 있다.

## Claude Code vs Cowork

| 항목 | Claude Code | Cowork |
|---|---|---|
| 주 무대 | 개발 작업 | 지식 업무 |
| 핵심 산출물 | 코드, 테스트, 수정 결과 | 문서, 브리프, 정리 결과 |
| 사용자 | 개발자 | 비개발 실무자 |
| 중요한 감각 | 범위와 검증 | 파일 구조와 승인선 |
| 위험 포인트 | 과도한 수정, 검증 누락 | 보안, 인젝션, 데이터 유출 |

이 둘을 쉬운 버전과 어려운 버전으로 이해하면 틀린다.
차이는 난이도가 아니라 **작업 모델**이다.

# 9. 실패 패턴 모음

성공 사례보다 실패 패턴이 더 오래 남는다.

## 실패 1. 너무 넓게 맡긴다
- 증상: 엉뚱한 파일까지 건드린다
- 원인: 범위가 없다
- 해결: 읽을 범위, 금지선, 출력 형식을 같이 준다

## 실패 2. 한 세션에 너무 많은 일을 섞는다
- 증상: 비싸고 느려지고 흐려진다
- 원인: 작업 분리가 없다
- 해결: 세션을 나누고 상시 규칙과 임시 작업을 분리한다

## 실패 3. 검증 없이 결과만 믿는다
- 증상: 그럴듯한데 불안하다
- 원인: 검증 루프가 없다
- 해결: 테스트, 체크리스트, 재현 기준을 붙인다

## 실패 4. 비개발 업무는 안전하다고 착각한다
- 증상: 자료 정리나 브라우저 작업을 가볍게 본다
- 원인: 문서, 브라우저, 외부 자료에 대한 보안 감각이 부족하다
- 해결: 승인선, 권한 최소화, 외부 자료 불신 원칙을 둔다

# 10. 실전 자산 모음

## 버그 수정
- 이 버그를 바로 고치지 말고, 먼저 재현 경로와 원인 가설부터 정리해줘.
- 관련 파일만 보고 가장 작은 수정으로 해결해줘.
- 수정하고 끝내지 말고, 어떤 방식으로 확인했는지 같이 적어줘.

## PR 리뷰
- 이 PR에서 스타일보다 먼저 기능 리스크, 회귀 가능성, 테스트 누락 여부를 봐줘.
- 고쳐야 할 부분만 분명하게 적고, 왜 문제인지도 같이 적어줘.

## 회의록 정리
- 이 회의 메모를 읽고 결정된 것, 아직 안 정해진 것, 다음 액션으로 나눠줘.
- 누가 무슨 말을 했는지보다 이번 주에 실제로 뭘 해야 하는지가 보이게 다시 써줘.

## 주간 브리프
- 이번 주에 새로 바뀐 점만 정리해줘.
- 마지막에 지금 당장 할 만한 액션 3개만 제안해줘.

## 경쟁사 분석
- 경쟁사가 뭘 잘하는지보다, 우리랑 어디서 갈리는지가 보이게 정리해줘.
- 메시지, 타깃, 강점, 약점, 차별점 기준으로 표로 정리해줘.

## 카피 다듬기
- 이 문장을 더 짧고 또렷하게 다듬어줘.
- 영어를 옮긴 것처럼 어색한 표현은 자연스러운 한국어로 바꿔줘.
- 톤이 다른 버전 3개를 줘. 직설적인 버전, 세련된 버전, 대중적인 버전.

## handoff
- 지금까지 한 일, 아직 안 끝난 일, 남은 리스크, 다음에 제일 먼저 볼 것을 순서대로 정리해줘.
- 이번 작업에서 실제로 바뀐 것만 짧게 정리해줘.

좋은 템플릿은 문장을 예쁘게 만드는 도구가 아니다.
작업을 덜 흔들리게 만드는 장치다.

# 11. 디자인 시스템 요약

좋은 가이드는 내용만 좋다고 끝나지 않는다.
읽히는 구조가 있어야 한다.

## 핵심 원칙
- 한 페이지엔 메시지 하나
- 설명보다 비교가 먼저
- 표와 카드 중심으로 구성
- 여백을 아끼지 않는다
- 강한 헤드라인, 짧은 본문, 한 줄 결론으로 리듬을 만든다

## 꼭 들어가야 할 페이지 타입
- 히어로 카피 페이지
- 한 장 요약 페이지
- 좋은 방식 vs 나쁜 방식 비교 페이지
- 역할별 플레이북 페이지
- 실패 패턴 치트시트
- 보안과 검수 경계 카드

이 가이드는 교재처럼 보이면 안 된다.
선명하고, 날카롭고, 읽기 쉬워야 한다.

# 마지막으로

Claude를 설명하는 문서는 많다.
하지만 Claude와 일하는 방식을 설계하는 문서는 드물다.

잘 쓰는 사람은 기능을 많이 아는 사람이 아니다.
어디에 맡길지, 어디서 멈출지, 무엇을 남길지, 어떻게 검수할지를 먼저 정하는 사람이다.

처음부터 완벽하게 맡기지 마라.
작고 되돌리기 쉬운 일부터 맡겨라.
그 작은 성공을 반복해서 작업 구조를 키워라.

그게 결국 Claude를 제대로 쓰는 가장 빠른 길이다.
