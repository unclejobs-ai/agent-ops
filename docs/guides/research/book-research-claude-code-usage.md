# Claude Code 실사용 패턴 리서치 메모

- 작성 목적: 책 챕터 **「Claude Code를 실제로 어떻게 쓰는가」**의 근거 자료
- 작성 언어: 한국어
- 조사 기준: Anthropic 공식 문서 + 공식 저장소/공개 자료 중심. 검색 API 제약으로 인해 비공식 블로그 대량 수집보다는 **공식 문서에서 반복적으로 강조하는 실사용 패턴**과 **공개 저장소/문서에 드러난 워크플로**를 우선 정리함.
- 핵심 결론 한 줄: **Claude Code를 잘 쓰는 사람은 “질문”을 잘하는 사람이 아니라, “검증 가능한 작업 루프”를 설계하는 사람이다.**

---

## 1. 먼저 잡아야 할 큰 그림

Claude Code는 단순 채팅형 코딩 도구가 아니라, **코드 읽기 + 파일 수정 + 명령 실행 + 검증 + git 작업**까지 한 세션 안에서 수행하는 에이전트형 도구다. 공식 문서가 계속 강조하는 것도 “답변을 잘 받는 법”보다 **탐색 → 계획 → 구현 → 검증 → PR**의 흐름이다.

공식 문서 기준으로 보면, 실제 사용은 대체로 아래 8개 패턴으로 수렴한다.

1. 버그 재현/수정
2. 리팩터링
3. 낯선 코드베이스 온보딩
4. PR 작성/리뷰
5. 테스트 생성/보강
6. 컨텍스트 관리
7. 권한/안전 모드 운용
8. 비용 통제

이 8개는 각각 따로 노는 기능이 아니라, 실제로는 서로 연결된다. 예를 들어:

- 온보딩을 잘해야 버그 수정이 빨라지고,
- Plan Mode를 잘 써야 리팩터링이 덜 위험하며,
- 컨텍스트 관리를 잘해야 비용과 정확도가 같이 좋아지고,
- 권한 모드를 맞게 골라야 실제 작업 속도가 올라간다.

## 2. 사용 패턴 1 — 버그 수정: “증상 설명”보다 “재현 루프 제공”이 더 중요하다

### 사람들이 실제로 어떻게 쓰는가

공식 워크플로 문서는 버그 수정에서 다음 흐름을 권한다.

1. 에러 메시지/증상 제공
2. 재현 명령 제공
3. 스택 트레이스나 재현 단계 제공
4. Claude가 원인 후보를 찾게 함
5. 수정 후 테스트/빌드/검증을 다시 돌리게 함

대표 예시:

- “`npm test`를 실행하면 이런 에러가 난다”
- “로그인 세션 타임아웃 이후 로그인 실패가 재현된다”
- “실패 테스트를 먼저 만들고, 그 후 고쳐라”

공식 Best Practices는 특히 **‘root cause를 해결하고, suppression으로 덮지 말라’**를 강조한다. 즉, “빨간 줄 없애기”가 아니라 **재현 가능한 실패를 성공으로 바꾸는 것**이 핵심이다.

### 좋은 프롬프트 패턴

- 나쁜 요청:
  - “로그인 버그 고쳐줘”
- 좋은 요청:
  - “세션 타임아웃 이후 로그인 실패가 난다. `src/auth/`의 token refresh 흐름을 확인해라. 먼저 실패 테스트를 만들고, 그 테스트가 통과하도록 수정한 뒤 전체 관련 테스트를 다시 돌려라.”

### 흔한 실수

1. **증상만 주고 재현 조건을 안 준다**
   - Claude가 넓게 추측하며 읽어야 해서 시간과 토큰이 늘어난다.
2. **스택 트레이스 없이 ‘뭔가 안 된다’고만 말한다**
   - 문제 범위가 너무 넓어진다.
3. **검증 기준 없이 수정만 시킨다**
   - “고친 것처럼 보이는” 패치를 만들기 쉽다.
4. **원인 제거 대신 예외 무시/ts-ignore/조건 완화로 끝낸다**
   - Anthropic 문서가 경계하는 전형적인 반패턴이다.

### 더 깊은 인사이트

Claude Code에서 버그 수정은 사실상 **‘진단 자동화’ 작업**이다. 즉, 사람의 역할은 “해결책 제안”이 아니라 **재현 환경과 정답 판별기를 공급하는 것**에 가깝다. 공식 문서가 테스트, 스크린샷, 기대 출력 등 **self-verification 수단**을 계속 요구하는 이유가 여기에 있다.

즉, 좋은 사용자는 이렇게 일한다.

- 문제를 설명한다 → X
- 문제를 **측정 가능하게 만든다** → O

## 3. 사용 패턴 2 — 리팩터링: 바로 고치게 하지 말고, Plan Mode로 한 번 ‘설계 분리’하기

### 사람들이 실제로 어떻게 쓰는가

공식 Common Workflows와 Best Practices는 리팩터링에서 공통적으로 다음 루프를 권한다.

1. **탐색**: 레거시 패턴/deprecated API/결합 관계 파악
2. **계획**: 어떤 파일을 왜 바꿔야 하는지 명시
3. **구현**: 작은 단위로 수정
4. **검증**: 동작 동일성 확인, 테스트 재실행

특히 Anthropic은 **Explore first, then plan, then code**를 거의 운영 원칙처럼 밀고 있다.

### 좋은 프롬프트 패턴

- “deprecated API 사용처를 찾아라”
- “`utils.js`를 현대 JS 문법으로 바꾸되, 동작은 동일하게 유지해라”
- “이 리팩터링의 backward compatibility 리스크를 적어라”
- “계획만 먼저 써라. 아직 수정하지 마라”

### 왜 Plan Mode가 중요한가

Plan Mode에서는 Claude가 읽고 조사할 수는 있지만, 함부로 소스 수정은 못 한다. 이 때문에 다음 상황에서 특히 유용하다.

- 다중 파일 리팩터링
- 구조 변경이 필요한 기능 추가
- 아직 코드베이스를 잘 모를 때
- 변경 파급이 큰 인증/데이터 계층 수정

즉, Plan Mode는 단순 안전장치가 아니라 **문제 정의를 구현에서 분리하는 사고 도구**다.

### 흔한 실수

1. **리팩터링과 재설계를 구분하지 않는다**
   - “깔끔하게 해줘”는 거의 항상 과도한 변경을 부른다.
2. **동작 동일성 조건을 명시하지 않는다**
   - “더 현대적으로”만 말하면 기능까지 달라질 수 있다.
3. **한 번에 크게 바꾸게 한다**
   - 테스트가 있어도 원인 역추적이 어려워진다.
4. **계획 없이 바로 수정 모드로 들어간다**
   - Claude가 틀린 추상화 위에 성실하게 코드를 쌓는 경우가 생긴다.

### 더 깊은 인사이트

Claude Code의 리팩터링 생산성은 모델 성능보다 **작업 분해 방식**에 더 크게 좌우된다. 사람은 “좋은 diff 경계”를 제공해야 한다. 공식 문서가 작은 단위, 테스트 가능한 단위, 계획 승인 단계를 권하는 이유다.

실전 문장으로 바꾸면:

- “이 파일을 개선해줘”보다
- “A를 B 패턴으로 옮기되, C API는 유지하고, D 테스트가 계속 통과해야 한다”가 훨씬 강하다.

## 4. 사용 패턴 3 — 코드베이스 온보딩: ‘설명 요청’보다 ‘지도 만들기’가 먼저다

### 사람들이 실제로 어떻게 쓰는가

공식 문서는 새 코드베이스 진입 시 다음 질문들을 제안한다.

- 이 코드베이스 구조를 개괄해줘
- 주요 아키텍처 패턴은 뭐야?
- 핵심 데이터 모델은 뭐야?
- 인증은 어떻게 처리돼?
- 특정 기능 관련 파일을 찾아줘
- 프론트엔드에서 DB까지 실행 흐름을 추적해줘

즉, 초반 온보딩의 핵심은 “파일 설명”이 아니라 **구조적 지도 생성**이다.

### 실전 활용 패턴

온보딩은 보통 3단계로 나눌 수 있다.

#### 1) 지도 만들기
- 주요 디렉터리
- 엔트리포인트
- 도메인 경계
- 데이터 모델
- 외부 의존성

#### 2) 흐름 추적
- 로그인 흐름
- 결제 흐름
- API 호출 흐름
- 렌더링/상태 관리 흐름

#### 3) 규칙 파악
- 코드 스타일
- 테스트 방식
- 배포 흐름
- 팀이 반복해서 지키는 관습

### 컨텍스트 도구와의 연결

공식 문서는 이 지점을 위해 `CLAUDE.md`, auto memory, skills, code intelligence plugin을 권한다. 이유는 간단하다. 온보딩 단계에서 매번 같은 구조 탐색을 반복하면 토큰이 많이 들고, 이후 작업의 정확도도 떨어진다.

### 흔한 실수

1. **첫 질문부터 구현을 시킨다**
   - 코드베이스를 모르는 상태에서 수정하면 확률적으로 맞을 뿐이다.
2. **‘전체 설명’만 받고 끝낸다**
   - 실행 흐름과 경계 조건을 못 잡는다.
3. **프로젝트 규칙을 메모리로 외우게 기대한다**
   - Claude는 세션 시작마다 새 컨텍스트로 시작한다. 문서화가 필요하다.
4. **CLAUDE.md에 모든 걸 때려 넣는다**
   - 오히려 기본 컨텍스트가 비대해진다.

### 더 깊은 인사이트

온보딩에서 Claude Code의 최고 사용법은 “사수처럼 설명하게 만들기”가 아니라 **반복 탐색을 구조화된 메모리로 변환하는 것**이다. 즉:

- 자주 쓰는 빌드/테스트 명령 → `CLAUDE.md`
- 프로젝트 구조/용어/패턴 → skills 또는 concise CLAUDE.md
- 개인 취향/실험 설정 → local settings
- 세션 중 발견한 사실 → auto memory

좋은 팀은 Claude를 똑똑한 신입처럼 대하지 않는다. **문서를 읽으면 바로 전력화되는 팀원**처럼 만든다.

## 5. 사용 패턴 4 — PR 작성과 리뷰: Claude를 ‘리뷰 대행자’보다 ‘리뷰 준비 엔진’으로 쓰는 편이 강하다

### 사람들이 실제로 어떻게 쓰는가

공식 문서에는 두 층위가 있다.

1. **로컬/개인 세션에서 PR 준비**
   - 변경 요약
   - 커밋 메시지 생성
   - PR 설명 작성
   - 리스크/체크리스트 보강
2. **조직 차원의 자동 Code Review**
   - GitHub PR에 인라인 코멘트
   - 다중 에이전트 병렬 분석
   - 심각도 구분
   - `CLAUDE.md`/`REVIEW.md`로 리뷰 기준 조정

### 개인 사용자의 현실적 활용법

실제 현업에서는 Claude Code를 아래처럼 쓰는 게 효율적이다.

- “내 변경 요약해줘”
- “이 PR 설명을 더 구체적으로 써줘”
- “이 변경의 위험 요소를 먼저 적어줘”
- “보안/회귀 관점에서 셀프 리뷰해줘”
- “diff 기준으로 리뷰 코멘트 후보를 뽑아줘”

즉, Claude를 **최종 승인자**가 아니라 **자기 리뷰를 강화하는 도구**로 쓰는 편이 실용적이다.

### 조직 차원 리뷰 기능에서 읽을 점

Code Review 문서는 Claude가 PR 리뷰에서 기본적으로 **스타일보다 correctness**를 본다고 설명한다. 이건 중요한 시사점이 있다.

- 린터가 잡을 것: 다른 도구로 처리
- 사람 리뷰어가 피곤해서 놓치는 것: Claude에게 맡김
- 팀 특화 규칙: `REVIEW.md`에 명시

### 흔한 실수

1. **PR 설명을 Claude가 대신 써줬다고 끝낸다**
   - 사실 관계/범위/리스크 점검은 사람이 해야 한다.
2. **스타일 리뷰까지 Claude에 과도하게 기대한다**
   - 포맷터/린터/정적 분석기가 더 싸고 정확하다.
3. **리뷰 기준을 문서화하지 않는다**
   - 그러면 매 PR마다 같은 규칙을 다시 프롬프트해야 한다.
4. **푸시마다 자동 리뷰를 걸어 비용 폭증**
   - Code Review는 평균 비용이 결코 싸지 않다.

### 더 깊은 인사이트

Claude Code의 PR 가치는 “대신 리뷰해줌”보다 **리뷰의 선행 작업을 자동화해 사람 리뷰어의 대역폭을 아껴주는 것**에 있다. 좋은 팀은 이렇게 분업한다.

- 포맷/스타일: 기계적 도구
- correctness 1차 스캔: Claude
- 제품/도메인/우선순위 판단: 사람

## 6. 사용 패턴 5 — 테스트 생성: ‘테스트를 써줘’보다 ‘어떤 실패를 잡아야 하는지’를 지정해야 한다

### 사람들이 실제로 어떻게 쓰는가

공식 문서는 테스트 업무를 아래 순서로 제안한다.

1. 테스트 없는 함수/모듈 탐색
2. 테스트 스캐폴딩 생성
3. edge case 추가
4. 실행 후 실패 수정

즉, 테스트 생성은 단순 코드 생성이 아니라 **커버리지 탐색 + 케이스 설계 + 실행 피드백**의 루프다.

### 좋은 프롬프트 패턴

- “이 서비스에서 테스트가 없는 함수부터 찾아라”
- “기존 테스트 스타일을 따라 새 테스트를 추가해라”
- “boundary condition과 error path를 더 추가해라”
- “새 테스트를 실행하고 깨지는 부분까지 고쳐라”

### 왜 기존 패턴 참조가 중요한가

Claude는 프로젝트 안의 기존 테스트 파일을 보고 assertion 스타일, fixture 패턴, mocking 관례를 맞추는 쪽이 훨씬 안정적이다. 그래서 단순히 “테스트 작성”보다:

- 참고 파일 지정
- mock 사용 여부 지정
- integration vs unit 테스트 지정
- 커버할 시나리오 지정

이 중요하다.

### 흔한 실수

1. **존재 가치가 낮은 테스트를 대량 생성**
   - 구현 복붙형 테스트가 늘어난다.
2. **happy path만 추가**
   - 실제 회귀를 못 잡는다.
3. **테스트는 만들고 실행은 안 시킴**
   - ‘테스트처럼 생긴 코드’만 생긴다.
4. **프로젝트 컨벤션을 무시**
   - 유지보수성이 떨어진다.

### 더 깊은 인사이트

Claude Code가 테스트에서 특히 강한 지점은 **사람이 쉽게 빼먹는 edge case 열거**다. 반대로 약한 지점은 **무엇이 중요한 edge case인지의 우선순위 판단**이다. 따라서 사람은 중요도를 지정하고, Claude는 케이스 공간을 넓히는 역할을 맡기는 편이 좋다.

## 7. 사용 패턴 6 — 컨텍스트 관리: 성능, 품질, 비용이 한 문제다

### 공식 문서가 반복해서 말하는 것

Best Practices와 Costs 문서 모두 핵심 제약으로 **컨텍스트 윈도우**를 든다. Claude는 대화, 읽은 파일, 명령 출력까지 모두 컨텍스트로 들고 가므로, 긴 세션일수록 품질이 떨어질 수 있다.

공식 권장 수단:

- `/clear`로 작업 전환 시 세션 초기화
- `/compact`로 중요한 것만 남기기
- status line이나 `/context`로 사용량 보기
- CLAUDE.md를 짧게 유지
- 세부 지침은 skills로 이동
- 고용량 작업은 subagent에 위임
- code intelligence plugin으로 탐색 효율 높이기
- hooks로 로그/테스트 출력 전처리

### 실사용 원칙

#### 1) 작업 단위를 세션 단위로 끊기
- 버그 하나
- 리팩터링 한 묶음
- PR 하나
- 테스트 보강 한 영역

이런 식으로 세션을 잘라야 한다.

#### 2) 장기 규칙과 단기 맥락을 분리하기
- 장기 규칙: `CLAUDE.md`
- 특정 업무 레시피: skill
- 현재 작업 진행상황: 세션 컨텍스트

#### 3) noisy output은 Claude 본체에 직접 먹이지 않기
- 긴 로그
- 방대한 테스트 출력
- 대량 파일 목록

가능하면 hook/subagent/필터링으로 줄여서 넘긴다.

### 흔한 실수

1. **하루 종일 한 세션에 다 몰아넣기**
   - 초반 품질과 후반 품질이 달라진다.
2. **CLAUDE.md를 백과사전처럼 키우기**
   - 항상 로드되므로 토큰 낭비가 크다.
3. **전문 작업 지침을 base context에 둔다**
   - 리뷰 규칙, DB 마이그레이션 절차, 배포 절차는 skill이 더 낫다.
4. **verbose 작업을 메인 세션에서 처리**
   - 테스트/로그/문서 수집은 subagent가 유리하다.

### 더 깊은 인사이트

Claude Code를 잘 쓰는 것은 사실상 **컨텍스트 운영체제(context OS)**를 설계하는 일과 비슷하다. 같은 모델을 써도,

- 세션을 짧고 목적별로 유지하는 팀,
- instructions를 계층화한 팀,
- noisy data를 압축해서 주는 팀

이 훨씬 높은 체감 성능을 얻는다.

## 8. 사용 패턴 7 — 권한/안전 모드: 속도를 올리려면 더 위험한 모드가 아니라 ‘작업에 맞는 모드’를 골라야 한다

### 공식 모드 정리

권한 관련 공식 문서에는 대략 다음 모드가 나온다.

- `default`: 읽기 중심, 작업마다 승인
- `acceptEdits`: 파일 수정은 매끄럽게
- `plan`: 읽고 조사하되 수정은 안 함
- `auto`: 자동 승인 + 백그라운드 안전 분류기
- `dontAsk`: 미리 허용한 것만 가능
- `bypassPermissions`: 거의 무제한, 격리 환경 전용

### 현실적인 사용 패턴

#### 1) 온보딩/조사
- `plan`
- 이유: 실수로 수정하지 않음

#### 2) 중간 크기 구현/리팩터링
- `acceptEdits`
- 이유: 편집 마찰은 줄이고, 쉘/네트워크는 계속 통제 가능

#### 3) 장시간 반복 작업
- `auto` (가능한 환경에서)
- 이유: 승인 피로를 줄임
- 단, 민감 작업에는 여전히 과신 금지

#### 4) 격리된 컨테이너/VM 실험
- `bypassPermissions`
- 이유: 오직 완전히 격리된 환경일 때만

### 흔한 실수

1. **속도가 안 나니 무조건 bypass로 간다**
   - 공식 문서도 강하게 경고한다.
2. **채팅에서 ‘이제부터 허락 없이 해’라고 말하면 모드가 바뀐다고 착각**
   - 실제 모드는 UI/설정/CLI 플래그로 바꿔야 한다.
3. **권한 규칙을 Bash 패턴만으로 안전하게 만들 수 있다고 믿는다**
   - 문서가 명확히 말하듯 Bash 패턴은 취약하다.
4. **Read/Edit deny가 shell subprocess까지 막는다고 오해**
   - OS 레벨 격리가 아니면 불충분하다.

### 더 깊은 인사이트

권한 모드는 단지 보안 기능이 아니라 **작업 인터페이스의 성격을 바꾸는 장치**다. 잘 쓰는 사람은 모드를 신념처럼 고정하지 않는다. 작업 단계에 맞춰 바꾼다.

- 조사 단계는 read-heavy
- 구현 단계는 edit-heavy
- 장기 자동화는 classifier-heavy

즉, “Claude를 얼마나 믿느냐”보다 “지금 어떤 종류의 실수가 비싼가”로 모드를 선택하는 게 맞다.

## 9. 사용 패턴 8 — 비용 통제: 돈을 아끼는 법은 모델 교체보다 ‘쓸데없는 컨텍스트 제거’에 가깝다

### 공식 문서의 핵심 포인트

비용 문서에서 Anthropic은 다음을 강조한다.

- 평균 사용 비용 예시를 제시함
- `/cost`, `/stats`로 사용량 확인 가능
- 팀은 workspace spend limit 설정 가능
- Sonnet을 기본으로, Opus는 어려운 문제에만
- context가 클수록 비용 증가
- MCP 서버가 많을수록 기본 오버헤드 증가
- subagent 수가 늘면 팀 비용도 비례 증가
- extended thinking도 비용 증가 요인

### 실제 절약 포인트

#### 1) 세션을 분리한다
관련 없는 작업을 같은 세션에 오래 쌓아두지 않는 것이 가장 기본적이다.

#### 2) 무거운 지침을 base context에서 빼낸다
- CLAUDE.md는 핵심만
- 특수 워크플로는 skill로

#### 3) verbose 작업은 subagent로 격리한다
테스트 출력, 로그 분석, 문서 수집은 메인 컨텍스트를 더럽히지 않게 분리한다.

#### 4) 도구 오버헤드를 줄인다
불필요한 MCP 서버는 끄고, CLI로 충분한 건 CLI를 쓴다.

#### 5) 모델을 혼합한다
- 기본 작업: Sonnet
- 무거운 아키텍처/고난도 추론: Opus
- 탐색성 서브태스크: Haiku 가능

### 흔한 실수

1. **비용 문제를 ‘모델이 비싸서’로만 이해**
   - 실제로는 컨텍스트 운영 실패가 더 큰 원인일 수 있다.
2. **에이전트를 많이 띄우면 생산성이 항상 오른다고 믿음**
   - 작은 팀/작은 작업은 오히려 낭비다.
3. **긴 로그/출력을 그대로 메인 세션에 붓는다**
   - 이후 모든 턴이 비싸진다.
4. **Opus를 기본값으로 박아둔다**
   - 공식 문서도 Sonnet 우선 사용을 권한다.

### 더 깊은 인사이트

비용 최적화는 단순히 “싼 모델 쓰기”가 아니라 **고가의 추론을 필요한 순간에만 호출하는 파이프라인 설계**다. 이 점에서 Claude Code의 비용 문제는 곧 워크플로 설계 문제다.

## 11. 책에 넣기 좋은 핵심 주장 10개

1. **Claude Code는 ‘질의응답 도구’보다 ‘작업 루프 자동화 도구’로 봐야 한다.**
2. **가장 중요한 프롬프트 기술은 명문장 작성이 아니라 검증 기준 제공이다.**
3. **버그 수정에서는 해결책보다 재현 루프가 더 중요하다.**
4. **리팩터링은 Plan Mode로 사고와 구현을 분리할 때 품질이 급상승한다.**
5. **온보딩은 설명 받기가 아니라 코드베이스 지도를 만드는 과정이다.**
6. **테스트 생성은 코드 생산보다 edge case 탐색에서 진가가 크다.**
7. **컨텍스트 관리 실패는 정확도 저하와 비용 증가를 동시에 부른다.**
8. **권한 모드는 보안 옵션이 아니라 작업 단계에 맞춘 인터페이스 선택이다.**
9. **PR 리뷰에서 Claude의 강점은 스타일 지적보다 correctness 1차 스캔이다.**
10. **비용 절감의 본질은 모델 다운그레이드가 아니라 쓸데없는 컨텍스트 제거다.**

## 12. 저자가 독자에게 줄 수 있는 실전 체크리스트

### 작업 시작 전
- [ ] 이 작업의 성공 기준이 있는가?
- [ ] 재현 명령/실패 조건이 있는가?
- [ ] 관련 파일/모듈 범위를 줄였는가?
- [ ] 지금 Plan Mode가 필요한가?

### 작업 중
- [ ] Claude가 스스로 검증할 수 있는가?
- [ ] 테스트/빌드/스크린샷 비교가 가능한가?
- [ ] noisy output을 그대로 먹이고 있지 않은가?
- [ ] 세션이 너무 길어져 unrelated context가 쌓이지 않았는가?

### 작업 후
- [ ] 왜 고쳐졌는지 root cause 설명을 받았는가?
- [ ] PR 설명/리스크/회귀 포인트가 정리됐는가?
- [ ] 반복 규칙이 있다면 CLAUDE.md/skill로 승격했는가?

## 13. 책용 서술 포인트: “Claude Code를 잘 쓰는 사람”의 특징

잘 쓰는 사람은:

- 막연히 “해줘”라고 하지 않고,
- 검증 기준을 주고,
- 작업 범위를 줄이고,
- 모드를 바꿔가며,
- 세션을 정리하고,
- 반복 규칙은 문서화한다.

못 쓰는 사람은:

- 한 세션에 모든 일을 몰아넣고,
- vague prompt로 시작하고,
- 확인 없이 수정만 시키고,
- 권한 모드를 무작정 풀고,
- 결과를 PR 문장 수준에서만 소비한다.

따라서 이 책 챕터의 메시지는 도구 소개가 아니라, 아래 문장으로 정리할 수 있다.

> Claude Code의 생산성은 모델 성능보다 운영 방식에 더 크게 좌우된다.

## 15. 한 문장 요약

**Claude Code를 실제로 잘 쓰는 법은, 좋은 질문을 던지는 것이 아니라 좋은 작업 환경과 검증 루프를 Claude에게 제공하는 것이다.**
