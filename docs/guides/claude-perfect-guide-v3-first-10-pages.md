# PAGE 1

## 잘 쓰면 에이전트, 못 쓰면 비싼 챗봇

Claude를 단순히 “질문 잘 받아주는 AI”로 쓰는 사람은 생각보다 많다.  
그리고 대부분은 거기서 멈춘다.

하지만 진짜 차이는 그 다음부터 난다.
누군가는 Claude에게 질문하고 답만 받는다.  
누군가는 Claude에게 **일을 맡기고, 검수하고, 다시 쓰게 만들고, 작업 구조까지 고정한다.**

그 차이가 생산성 차이이고, 결과물 차이이고, 결국 실력 차이다.

이 가이드는 Claude를 설명하는 문서가 아니다.  
**Claude와 함께 일하는 방식을 설계하는 문서**다.

# PAGE 2

## 왜 어떤 사람은 10배 빨라지고, 어떤 사람은 토큰만 태울까

문제는 보통 모델이 아니다.
대부분의 문제는 아래 다섯 군데에서 터진다.

1. 작업면을 잘못 고른다
2. 범위를 안 정하고 맡긴다
3. 컨텍스트를 무작정 길게 넣는다
4. 검증 루프 없이 결과만 받는다
5. 권한과 보안 경계를 너무 늦게 생각한다

Claude를 잘 쓰는 사람은 프롬프트를 화려하게 쓰는 사람이 아니다.

- 어디에 맡길지 고르고
- 무엇만 보게 할지 정하고
- 어떻게 끝낼지 먼저 정하고
- 어떤 지점에서 사람이 다시 볼지 설계하는 사람

즉, 잘 쓰는 사람은 말을 잘하는 사람이 아니라  
**작업장을 잘 만드는 사람**이다.

# PAGE 3

## Claude는 하나가 아니다
### 같은 두뇌, 다른 작업대

Claude는 하나의 채팅창이 아니다.
지금의 Claude는 여러 작업면으로 나뉜 작업 시스템에 가깝다.

| 작업면 | 핵심 역할 | 한 줄 설명 |
|---|---|---|
| Chat | 질문과 빠른 정리 | 지금 바로 묻고 답받는 곳 |
| Projects | 배경 유지 | 같은 맥락을 오래 들고 가는 곳 |
| Cowork | 문서/파일 위임 | 비개발 업무를 구조적으로 맡기는 곳 |
| Claude Code | 구현/검증 | 코드와 테스트를 다루는 작업대 |

이걸 모르고 쓰면 문제가 생긴다.

- Chat으로 운영을 하려 하고
- Cowork로 깊은 구현을 하려 하고
- Claude Code로 브리프 초안을 만들려 하고
- Projects 없이 매번 같은 설명을 다시 붙인다

그렇게 되면 “Claude가 별로네”가 아니라  
**작업대 선택이 틀린 것**에 가깝다.

# PAGE 4

## 가장 쉬운 선택법
### 이 일, 어디에 올려야 하나

### Chat에 올릴 일
- 생각 정리
- 요약
- 빠른 초안
- 질문 재정리

### Projects에 올릴 일
- 장기 프로젝트 배경 유지
- 팀 공통 맥락 누적
- 계속 재사용할 전제 정리

### Cowork에 올릴 일
- 회의록 → 브리프
- 자료 정리
- 문서 초안
- 파일 기반 지식 업무

### Claude Code에 올릴 일
- 버그 수정
- 리팩터링
- 테스트 작성
- 구현 + 검증이 필요한 일

## 한 줄 판단

> 질문이면 Chat, 배경이면 Projects, 문서 위임이면 Cowork, 구현과 검증이면 Claude Code.

이 기준 하나만 잡아도 초반 시행착오가 크게 줄어든다.

# PAGE 5

## 좋은 요청은 길어서 좋은 게 아니다
### 좋은 요청은 경계가 있다

AI에게 일을 맡길 때 가장 흔한 실수는 “자세히 말하면 더 잘하겠지”라고 믿는 것이다.

문제는 길이가 아니라 구조다.

### 나쁜 요청
로그인 버그 고쳐줘.

### 좋은 요청
auth 관련 파일만 읽고, env와 배포 설정은 건드리지 말고, 먼저 원인 가설을 세운 뒤 가장 작은 수정으로 해결해 줘. 끝나면 바뀐 파일과 검증 결과를 정리해 줘.

둘의 차이는 단순하지 않다.
좋은 요청은 아래를 가지고 있다.

- 범위
- 금지선
- 작업 순서
- 결과 형식
- 검증 기준

즉, 좋은 요청은 Claude를 더 똑똑하게 만드는 게 아니라  
**덜 흔들리게 만든다.**

# PAGE 6

## 좋은 결과는 좋은 프롬프트보다 좋은 작업장에서 나온다

Claude가 망가지는 대표 패턴은 이렇다.

- 모든 파일을 다 보게 한다
- 다른 작업을 한 세션에 계속 섞는다
- 규칙과 예시와 결과물을 뒤섞는다
- 끝난 뒤 무엇을 확인할지 정하지 않는다

이건 프롬프트 문제가 아니라 작업장 문제다.

좋은 작업장은 이렇게 생긴다.

```text
workspace/
├── context/
├── projects/
├── templates/
├── outputs/
└── handoff/
```

이 구조가 중요한 이유는 간단하다.

- `context/` = 계속 알아야 할 것
- `projects/` = 이번 작업 자료
- `templates/` = 출력 기준
- `outputs/` = 생성 결과
- `handoff/` = 다음 사람이나 다음 세션을 위한 인수인계

긴 프롬프트보다 이런 구조가 훨씬 오래 간다.

# PAGE 7

## Claude Code의 핵심은 답변이 아니라 루프다
### 탐색 → 계획 → 실행 → 검증

Claude Code를 진짜 강하게 쓰는 사람은 한 번에 완벽한 답을 기대하지 않는다.
대신 루프를 만든다.

### 1. 탐색
관련 파일과 원인을 좁힌다.

### 2. 계획
무엇을 바꿀지, 왜 바꿀지 정리한다.

### 3. 실행
가장 작은 수정부터 적용한다.

### 4. 검증
테스트와 실제 동작 기준으로 확인한다.

많은 초보자가 2번과 4번을 건너뛴다.
그래서 처음엔 “와 잘하는데?” 싶다가,
뒤로 갈수록 **왜 바꿨는지 모르겠고, 믿기도 어려운 결과**를 받게 된다.

기억할 문장 하나면 충분하다.

> Claude가 스스로 검증할 수 있게 만들어라.

이 한 줄이 실전 품질을 바꾼다.

# PAGE 8

## 컨텍스트 관리가 실력이다

많이 넣는다고 잘되는 게 아니다.
오히려 너무 많이 넣으면:

- 느려지고
- 비싸지고
- 초점이 흐려지고
- 이상한 걸 붙잡고 오래 돈다

Claude는 지금 입력한 문장만 읽지 않는다.
함께 읽는 것들은 계속 늘어난다.

- 이전 대화
- 읽은 파일
- 규칙 파일
- 도구 실행 결과
- 방금 만든 출력

그래서 잘 쓰는 사람은 이렇게 생각한다.

> “무엇을 더 넣을까?”보다 “무엇을 빼야 덜 흐릴까?”

컨텍스트는 메모리가 아니라 작업 반경이다.
줄여야 선명해진다.

# PAGE 9

## 자동화는 사람을 없애는 기술이 아니다
### 사람이 꼭 봐야 할 지점을 줄이는 기술이다

AI 자동화를 말할 때 가장 많이 생기는 오해가 있다.

> “좋아, 그럼 이제 다 맡기면 되겠네?”

아니다.
진짜 좋은 운영은 모든 걸 자동화하지 않는다.
대신 **자동화 가능한 부분과 사람이 꼭 봐야 하는 부분을 분리한다.**

### 자동화하기 좋은 것
- 초안 쓰기
- 요약
- 정리
- 내부 브리프
- 테스트 실행

### 반드시 사람이 다시 봐야 하는 것
- 외부 발송
- 결제/정산
- 삭제
- 권한 변경
- 실제 배포

가이드가 강해지려면 성능보다 이 선을 분명히 해야 한다.
그래야 사용자도 믿고 쓴다.

# PAGE 10

## 강한 에이전트의 문제는 대답이 아니라 권한이다

AI가 더 많은 일을 할수록, 문제의 종류도 바뀐다.
예전에는 “틀린 답”이 문제였다면,
지금은 “틀린 행동”이 더 큰 문제가 된다.

- 엉뚱한 파일을 읽는다
- 외부 자료의 지시를 그대로 따른다
- 민감한 정보에 닿는다
- 잘못된 자동화를 계속 반복한다

그래서 강한 가이드는 기능을 자랑하는 문서가 아니라,
**권한과 보안 경계를 먼저 설계하는 문서**여야 한다.

Claude를 잘 쓴다는 건 더 과감하게 맡긴다는 뜻이 아니다.

어디까지 맡기고,
어디서 멈추고,
어디서 사람이 다시 잡아야 하는지 아는 것.

그게 진짜 운영 실력이다.
