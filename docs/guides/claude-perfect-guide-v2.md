# 1장. Claude를 챗봇처럼 쓰면 손해 보는 이유

## Claude는 하나가 아니다

많은 사람이 Claude를 그냥 “웹에서 쓰는 AI 채팅창” 정도로 이해한다.
그렇게만 보면 반밖에 못 쓴다.

지금의 Claude는 하나의 얼굴을 가진 제품이 아니라, **여러 작업면(surface)** 을 가진 작업 시스템에 가깝다.
같은 모델이라도 어디에서 쓰느냐에 따라 잘하는 일이 달라진다.

### 한 줄로 정리하면
- **Chat** = 지금 바로 묻고 정리하는 곳
- **Projects** = 같은 배경을 계속 들고 가는 곳
- **Cowork** = 문서와 파일 중심 작업을 맡기는 곳
- **Claude Code** = 구현, 수정, 테스트, 검증을 맡기는 곳

## 왜 이 구분이 중요한가

초보자는 보통 이렇게 생각한다.

> “제일 똑똑한 모델이 어디 있지?”

하지만 실무에서 더 중요한 질문은 이거다.

> “이 일을 어느 작업대에 올려놔야 덜 끊기고 덜 망하나?”

같은 Claude라도:
- Chat에선 질문 품질의 영향을 많이 받고
- Cowork에선 폴더 구조와 템플릿의 영향을 많이 받고
- Claude Code에선 작업 범위와 검증 루프의 영향을 많이 받는다

즉 차이는 모델 점수보다 **작업 구조**에서 더 크게 난다.

# 2장. 5분 만에 이해하는 Claude 작업면

## 2-1. 가장 빠른 비교표

| 작업면 | 가장 잘하는 일 | 약한 일 | 이런 사람에게 잘 맞음 |
|---|---|---|---|
| Claude Chat | 질문, 요약, 초안, 생각 정리 | 장기 운영, 복잡한 실행 | 모두 |
| Projects | 같은 배경 유지, 프로젝트 맥락 누적 | 직접 실행, 자동화 | PM, 연구자, 창업가 |
| Cowork | 파일 읽기, 문서 정리, 브리프 생성, 비개발 업무 위임 | 깊은 코드 수정 | 운영자, 마케터, 비개발 실무자 |
| Claude Code | 코드 탐색, 수정, 테스트, 리팩터링, 검증 | 광범위한 문서 업무 전체 | 개발자 |

## 2-2. 가장 흔한 오해

### 오해
“같은 Claude니까 어디서 써도 비슷하겠지.”

### 현실
같은 두뇌라도 **앉아 있는 책상**이 다르면 잘하는 일이 달라진다.

- 상담 창구에 앉히면 질문에 강하다
- 문서 책상에 앉히면 정리와 초안에 강하다
- 개발 작업대에 앉히면 구현과 검증에 강하다

이걸 이해하면 “왜 자꾸 기대한 대로 안 되지?”가 많이 풀린다.

# 3장. 어떤 일을 어디에 맡길까

## 3-1. 상황별 선택표

| 상황 | Chat | Projects | Cowork | Claude Code |
|---|---|---|---|---|
| 아이디어 정리 | 최고 | 보조 | 보통 | 과함 |
| 회의록 요약 | 좋음 | 보조 | 최고 | 과함 |
| 경쟁사 브리프 | 보통 | 좋음 | 최고 | 과함 |
| 긴 배경 문맥 유지 | 약함 | 최고 | 보통 | 보통 |
| 버그 수정 | 약함 | 보조 | 부적합 | 최고 |
| 테스트 작성/검증 | 약함 | 보조 | 부적합 | 최고 |
| 반복 문서 작업 | 보통 | 보조 | 최고 | 보통 |
| 리팩터링 | 약함 | 보조 | 부적합 | 최고 |

## 3-2. 초보자를 위한 가장 쉬운 판단법

### 이럴 때 Chat
- 지금 바로 생각을 정리하고 싶다
- 긴 문서를 짧게 압축하고 싶다
- 빠른 초안을 잡고 싶다

### 이럴 때 Projects
- 같은 프로젝트 배경을 계속 들고 가야 한다
- 매번 다시 설명하는 게 귀찮다
- 장기적으로 축적되는 문맥이 필요하다

### 이럴 때 Cowork
- 파일을 읽혀서 결과물을 만들고 싶다
- 회의록, 브리프, 문서 초안, 자료 정리를 맡기고 싶다
- 비개발 업무를 더 구조적으로 위임하고 싶다

### 이럴 때 Claude Code
- 코드를 수정해야 한다
- 테스트와 검증까지 해야 한다
- 리팩터링, 디버깅, 구현 같은 작업을 맡겨야 한다

# 4장. 좋은 첫 과제와 나쁜 첫 과제

## 좋은 첫 과제

처음에는 **작고, 되돌리기 쉽고, 끝이 보이는 일**부터 맡기는 편이 좋다.

### 추천
- 보고서를 5문장 요약 + 3개 질문으로 정리하기
- 회의 메모를 주간 브리프로 바꾸기
- 버그 수정 전에 원인 가설과 수정 계획만 먼저 세우기
- 참고 자료를 템플릿 구조에 맞게 정리하기
- 반복 문서를 같은 형식으로 통일하기

## 나쁜 첫 과제

처음부터 아래처럼 시작하면 대체로 망한다.

### 비추천
- 외부 연결 도구를 첫날 전부 붙이기
- 범위 없이 “우리 서비스 전체 개선해줘”라고 던지기
- 사람 승인선 없이 메일 발송/삭제/정산 입력 자동화하기
- 예시나 규칙 없이 “우리 톤으로 다 알아서 해줘”라고 하기
- 코드베이스를 읽히자마자 신규 기능 전체를 맡기기

## 기억할 문장

> 처음에는 중요한 일을 빨리 맡기는 것보다, 작은 일을 안전하게 맡기는 것이 더 중요하다.

# 5장. 좋은 요청 vs 나쁜 요청

좋은 결과는 좋은 모델에서만 나오지 않는다.
대부분은 **좋은 작업 경계**에서 나온다.

## 예시 1. 버그 수정

### 나쁜 요청
로그인 버그 고쳐줘.

### 좋은 요청
auth 관련 파일만 읽고, env와 배포 설정은 건드리지 말고, 먼저 원인 가설을 세운 뒤 가장 작은 수정으로 해결해 줘. 끝나면 바뀐 파일과 검증 결과를 같이 남겨줘.

### 왜 좋은가
- 읽을 범위가 있다
- 건드리면 안 되는 영역이 있다
- 바로 수정하지 않고 원인부터 본다
- 끝난 뒤 검증 기준이 있다

## 예시 2. 주간 브리프

### 나쁜 요청
이번 주 시장 업데이트 만들어줘.

### 좋은 요청
이 메모와 링크를 읽고 이번 주에 바뀐 점만 요약해 줘. 우리에게 왜 중요한지 설명하고, 마지막에는 액션 아이템 3개만 제안해 줘.

### 왜 좋은가
- 범위가 있다
- 결과 형식이 있다
- 중요도 판단 기준이 있다
- 출력의 끝모양이 정해져 있다

## 예시 3. 코드 리뷰

### 나쁜 요청
이 PR 리뷰해줘.

### 좋은 요청
이 PR에서 기능 리스크, 회귀 가능성, 테스트 누락 여부만 중점적으로 봐줘. 스타일보다 실제 동작 위험을 먼저 찾고, 반드시 재현 가능한 우선순위 순으로 정리해 줘.

## 핵심 규칙

좋은 요청은 보통 아래 다섯 가지 중 최소 세 가지를 가진다.

1. 범위
2. 금지선
3. 작업 순서
4. 출력 형식
5. 검증 기준

# 6장. Claude Code의 핵심: 탐색 → 계획 → 실행 → 검증

Claude Code를 단순 터미널 챗봇처럼 쓰면 체감이 반토막 난다.
Claude Code의 강점은 **작업 흐름 전체**를 맡길 수 있다는 데 있다.

## 기본 흐름

### 1) 탐색
- 어떤 파일이 관련 있는지 찾는다
- 어디가 진짜 원인인지 좁힌다
- 읽을 범위를 줄인다

### 2) 계획
- 무엇을 바꿀지 정리한다
- 리스크를 먼저 드러낸다
- 큰 작업이면 단계로 쪼갠다

### 3) 실행
- 가장 작은 수정부터 적용한다
- 관련 없는 부분은 건드리지 않는다
- 필요한 코드만 바꾼다

### 4) 검증
- 테스트를 돌린다
- 실제 동작 기준으로 확인한다
- 남은 위험과 후속 작업을 정리한다

## 가장 중요한 원칙

> Claude가 스스로 검증할 수 있게 만들어라.

이건 단순 팁이 아니라, 실전에서 품질 차이를 만드는 핵심 원칙이다.
검증 없는 결과는 멋져 보여도 신뢰가 약하다.

# 7장. 컨텍스트 관리가 실력이다

많은 사람이 프롬프트를 더 길게 쓰면 결과가 좋아질 거라고 생각한다.
실제로는 정반대인 경우가 많다.

컨텍스트는 많다고 무조건 좋은 게 아니다.
너무 길어지면:
- 비용이 늘고
- 속도가 느려지고
- 성능이 흔들리고
- 초점이 흐려진다

## 7-1. 왜 컨텍스트 관리가 중요한가

Claude는 질문 한 줄만 읽는 게 아니다.
함께 들어가는 것들:
- 현재 요청
- 이전 대화
- 읽은 파일
- 규칙 파일
- 도구 실행 결과
- 모델이 직전에 만든 출력

즉, 컨텍스트는 성능이자 비용이자 집중력이다.

## 7-2. 무엇을 항상 넣고, 무엇을 필요할 때만 넣을까

### 항상 필요한 것
- 프로젝트의 기본 규칙
- 금지선
- 핵심 배경
- 자주 반복되는 작업 원칙

이런 건 `CLAUDE.md`나 상시 규칙 파일에 가깝다.

### 가끔 필요하지만 길고 구체적인 것
- 특정 작업 절차
- 반복 템플릿
- 상황별 상세 가이드

이런 건 Skill 쪽이 더 맞다.

### 따로 떼어내야 하는 것
- 로그 대량 분석
- 탐색량이 큰 조사 작업
- 메인 작업과 별개인 읽기 작업

이런 건 subagent처럼 **별도 문맥에서 처리하고 요약만 가져오는 방식**이 유리하다.

## 7-3. 컨텍스트를 망치는 대표 패턴

- 저장소 전체를 한 번에 읽히기
- 긴 대화 안에서 계속 다른 작업 섞기
- 규칙/예시/결과물을 한 세션에 끝없이 누적하기
- 상시 규칙과 임시 지시를 구분하지 않기

## 한 줄 결론

> 잘 쓰는 사람은 프롬프트를 길게 쓰는 사람이 아니라, Claude가 읽을 문맥을 설계하는 사람이다.

# 8장. CLAUDE.md / Skill / Subagent / Hook / MCP 헷갈리지 않는 법

초보자가 가장 자주 막히는 구간이다.
이걸 기능 이름으로 외우면 헷갈리고, **역할**로 보면 바로 잡힌다.

## 8-1. 한 번에 이해하는 표

| 요소 | 한 줄 설명 | 언제 쓰나 | 비유 |
|---|---|---|---|
| CLAUDE.md | 항상 읽히는 기본 규칙 | 늘 필요한 공통 기준 | 작업장 운영수칙 |
| Skill | 필요할 때 불러오는 절차 | 반복 작업을 잘하게 할 때 | 업무 매뉴얼 |
| Subagent | 별도 문맥에서 일하는 작업자 | 읽기/조사/분리 작업 | 외부 조사 담당자 |
| Hook | LLM 없이 자동으로 도는 규칙 | 항상 같은 검사를 강제할 때 | 자동 검사기 |
| MCP | 외부 도구와 연결하는 길 | Slack, Drive, GitHub 등에 닿아야 할 때 | 외부 배선 |

## 8-2. 가장 쉬운 판단법

### “늘 필요한 규칙인가?”
그러면 `CLAUDE.md`

### “가끔 필요하지만 매번 같은 절차인가?”
그러면 Skill

### “이 작업은 문맥을 너무 많이 먹는가?”
그러면 Subagent

### “이건 AI가 판단할 일이 아니라 무조건 검사해야 하는가?”
그러면 Hook

### “밖의 도구에 닿아야 하는가?”
그러면 MCP

# 9장. 자동화는 어디까지 맡기고, 어디서 사람을 세워야 하나

좋은 가이드는 성능만 말하지 않는다.
**어디서 멈춰야 하는지도** 말한다.

## 자동화 가능한 영역
- 초안 작성
- 회의록 정리
- 내부 브리프 생성
- 코드 수정 제안
- 테스트 실행
- 대량 정리 작업

## 사람 검수가 반드시 필요한 영역
- 외부 발송
- 결제/정산
- 삭제
- 배포
- 권한 변경
- 법무/민감 정보 처리
- 되돌리기 어려운 작업

## 한 장 판단표

| 작업 | 자동화 가능 | 사람 검수 |
|---|---|---|
| 초안 쓰기 | 높음 | 필요 |
| 요약 | 높음 | 권장 |
| 내부 문서 정리 | 높음 | 권장 |
| 코드 수정 | 중간 | 필요 |
| 테스트 실행 | 높음 | 결과 검토 필요 |
| 외부 발송 | 낮음 | 필수 |
| 삭제/결제/권한 | 매우 낮음 | 필수 |

## 기억할 문장

> 자동화의 핵심은 사람을 없애는 게 아니라, 사람이 꼭 봐야 할 지점을 줄이는 것이다.

# 10장. 비용 통제: 왜 어떤 사람은 토큰만 태울까

Claude를 잘 쓰는 사람과 못 쓰는 사람의 차이는 성능보다 운영 습관에서 더 크게 난다.

## 비용이 터지는 대표 패턴
- 저장소 전체를 매번 다시 읽힘
- 같은 배경을 긴 대화에 계속 누적함
- 한 세션에서 너무 많은 작업을 섞음
- 필요한 파일만 주지 않고 전부 던짐
- 읽기 작업과 실행 작업을 분리하지 않음

## 비용을 줄이는 기본 원칙
1. 작업을 작게 나눈다
2. 관련 파일만 읽힌다
3. 상시 규칙과 임시 지시를 분리한다
4. 탐색량이 큰 일은 별도 작업자로 뺀다
5. 결과만 남기고 불필요한 문맥은 줄인다

## 가장 중요한 오해

### 오해
컨텍스트를 많이 주면 무조건 더 잘한다.

### 현실
필요한 것만 정확히 주는 편이 대체로 더 싸고 더 안정적이다.

# 11장. 보안과 권한: 강한 에이전트일수록 더 중요하다

AI가 더 많은 일을 할수록, 더 많은 권한 문제가 따라온다.
좋은 가이드는 이걸 뒤에 숨기지 않는다.

## 11-1. 왜 위험이 커지는가

Claude가 파일, 브라우저, 커넥터, 명령 실행까지 다루기 시작하면
문제는 “틀린 답”이 아니라 “틀린 행동”으로 바뀐다.

즉 위험도 달라진다.
- 수상한 파일을 읽을 수 있고
- 외부 지시를 섞어 받을 수 있고
- 민감한 정보에 닿을 수 있고
- 잘못된 자동화가 더 넓게 퍼질 수 있다

## 11-2. 기본 보안 습관

- 처음부터 권한을 넓게 열지 말 것
- 신뢰되지 않은 자료는 그대로 믿지 말 것
- 외부 발송, 삭제, 배포는 승인선을 둘 것
- 읽기용 작업과 실행용 작업을 분리할 것
- 중요한 작업은 로그와 결과를 남길 것

## 11-3. Cowork 같은 일반 업무 에이전트에서 더 조심해야 하는 이유

비개발 업무라고 해서 덜 위험한 게 아니다.
오히려:
- 파일 범위가 넓고
- 브라우저 상호작용이 많고
- 일반 사용자는 보안 감각이 약할 수 있어서
위험 반경이 커질 수 있다.

## 기억할 문장

> 강한 에이전트의 문제는 대답이 아니라 권한이다.

# 12장. Claude Code vs Chat형 AI vs IDE 보조도구

많은 비교가 “누가 더 똑똑하냐”에 머문다.
실무자는 그렇게 비교하면 안 된다.

## 더 좋은 비교 질문

- 누가 프로젝트 전체를 더 잘 읽나?
- 누가 작업을 통째로 맡기기 좋나?
- 누가 테스트와 검증까지 연결되나?
- 누가 장기 세션 운영에 강한가?
- 누가 더 관찰 가능하고 제어 가능한가?

## 비교표

| 비교축 | Chat형 AI | IDE 코파일럿류 | Claude Code |
|---|---|---|---|
| 질문 응답 | 강함 | 약함 | 보통 |
| 프로젝트 전체 탐색 | 약함 | 보통 | 강함 |
| 셸/명령 실행 | 거의 없음 | 제한적 | 강함 |
| 검증 루프 | 약함 | 보통 | 강함 |
| 큰 작업 위임 | 약함 | 보통 | 강함 |
| 장기 운영 구조 | 약함 | 보통 | 강함 |

## 한 줄 결론

> Claude Code의 진짜 경쟁력은 “코드 제안”이 아니라 “작업 전체를 맡길 수 있는가”에 있다.

# 13장. Claude Code vs Cowork

이 둘을 쉬운 버전/어려운 버전으로 이해하면 틀린다.
핵심 차이는 난이도가 아니라 **작업 모델**이다.

## Claude Code
- 코드 중심
- 구현과 검증 중심
- 통제력이 강함
- 개발자가 중간 단계를 세밀하게 볼 수 있음

## Cowork
- 문서/파일/브라우저/지식업무 중심
- 위임과 결과물 생성 중심
- 비개발자도 진입하기 쉬움
- 대신 보안/권한/감사 가능성을 더 신경 써야 함

## 비교표

| 항목 | Claude Code | Cowork |
|---|---|---|
| 주 무대 | 개발 작업 | 지식 업무 |
| 핵심 산출물 | 코드, 테스트, 수정 결과 | 문서, 브리프, 정리 결과 |
| 사용자 | 개발자 | 비개발 실무자 |
| 중요한 감각 | 범위와 검증 | 파일 구조와 승인선 |
| 위험 포인트 | 과도한 수정, 검증 누락 | 보안, 인젝션, 데이터 유출 |

# 14장. 실패 패턴으로 배우는 진짜 운영법

성공 사례보다 실패 패턴이 더 오래 남는다.

## 실패 1. 너무 넓게 맡김
### 증상
엉뚱한 파일까지 건드린다.

### 원인
범위가 없다.

### 해결
읽을 범위, 금지선, 출력 형식을 같이 준다.

## 실패 2. 토큰이 갑자기 많이 든다
### 증상
세션이 길어질수록 비싸고 느려진다.

### 원인
작업을 안 나누고 문맥을 계속 쌓는다.

### 해결
작업을 분리하고, 상시 규칙과 임시 작업을 나눈다.

## 실패 3. 똑똑해 보이는데 불안하다
### 증상
결과는 그럴듯하지만 믿기 어렵다.

### 원인
검증 루프가 없다.

### 해결
테스트, 체크리스트, 재현 기준을 붙인다.

## 실패 4. 비개발 업무라 방심한다
### 증상
자료 정리나 브라우저 작업은 안전할 거라 생각한다.

### 원인
문서/브라우저/외부 자료에 대한 보안 감각 부족.

### 해결
승인선, 권한 최소화, 외부 자료 불신 원칙을 둔다.

# 15장. 이 가이드를 프리미엄하게 만드는 디자인 문법

좋은 가이드는 내용만 좋다고 완성되지 않는다.
읽히는 구조가 있어야 한다.

## 페이지 구성 원칙

### 1. 한 페이지, 한 메시지
한 페이지에서 주장 하나만 세게 말한다.

### 2. 설명보다 비교
긴 문단보다 비교 카드가 이해를 빠르게 만든다.

### 3. 글보다 구조
표, 카드, 체크리스트, 흐름도가 많을수록 초보자가 덜 지친다.

### 4. 밀도보다 리듬
모든 페이지를 빽빽하게 채우지 말고, 핵심 문장과 여백으로 호흡을 만든다.

## 반드시 들어가야 할 페이지 타입
- 히어로 카피 페이지
- 한 장 요약 지도
- 잘못된 방식 vs 올바른 방식 페이지
- 작업면 선택 매트릭스
- 역할별 플레이북
- 실패 패턴 치트시트
- 보안/검증 경계 카드

## 톤앤매너 원칙
- 날카롭되 과장하지 않는다
- 쉽게 쓰되 얕지 않다
- 친절하되 군더더기가 없다
- 실전 기준을 준다
- 저장하고 싶은 문장으로 끝낸다

# 16장. Claude Code Academy / Perfect Guide가 가져가야 할 포지션

우리가 이기는 방식은 단순하다.

## 우리가 하지 말아야 할 것
- 기능 백과사전처럼 쓰기
- 모든 메뉴를 다 설명하기
- 광고 문안처럼 생산성만 과장하기
- 비교를 피상적으로 하기

## 우리가 가져가야 할 자리

### 1. 기능 설명서가 아니라 운영 매뉴얼
언제 뭘 쓰는지, 왜 그렇게 쓰는지, 어디서 멈추는지까지 말해준다.

### 2. 초보자도 바로 쓰는 가이드
비유, 비교표, 나쁜 예시/좋은 예시, 역할별 플레이북이 많아야 한다.

### 3. 파워유저도 인정하는 기준서
컨텍스트, 비용, 보안, 검증, 투명성까지 다룬다.

### 4. 저장하고 공유하고 다시 보는 문서
정보가 많아서가 아니라, 판단 기준이 선명해서 다시 보게 만든다.

## 최종 한 줄

> 이 가이드는 Claude를 설명하는 문서가 아니라, Claude와 함께 일하는 방식을 설계하는 문서여야 한다.
