# Claude Perfect Guide
## Design System v1

이 문서는 Claude Perfect Guide를 PDF나 웹으로 펼칠 때 기준이 되는 디자인 규칙을 정리한 문서다.
핵심은 화려함이 아니라 **잘 읽히고, 빨리 이해되고, 저장하고 싶어지는 구조**다.

---

# 1. 전체 방향

이 가이드는 교재처럼 보이면 안 된다.
느낌은 아래 셋의 중간쯤 가야 한다.

- Apple처럼 선명하다
- Linear처럼 날카롭다
- Notion처럼 읽기 쉽다

즉, 정보가 많아도 답답하면 안 되고,
프리미엄해 보여도 허세처럼 보이면 안 된다.

---

# 2. 핵심 원칙

## 2-1. 한 페이지엔 메시지 하나
한 페이지에서 주장 하나만 세게 말한다.
여러 개를 욱여넣으면 읽는 사람이 기억하지 못한다.

## 2-2. 설명보다 비교가 먼저
긴 글보다 비교표 한 장이 더 빨리 이해된다.
가능하면 아래 우선순위를 따른다.

1. 비교표
2. 카드
3. 체크리스트
4. 짧은 설명 문단
5. 긴 설명 문단

## 2-3. 강약을 만든다
모든 문장을 똑같이 세게 쓰면 피곤하다.
강한 헤드라인, 짧은 본문, 한 줄 결론이 리듬을 만든다.

## 2-4. 여백을 아끼지 않는다
프리미엄 문서는 정보량으로 누르는 게 아니라,
**정보를 숨 쉬게 해서** 세 보이게 한다.

---

# 3. 페이지 타입

## 3-1. 히어로 페이지
문서 초반이나 큰 장 시작에 쓰는 페이지다.

### 구성
- 짧은 제목
- 한 줄 선언
- 2~4줄 설명
- 여백 넓게

### 예시
- 잘 쓰면 에이전트, 못 쓰면 비싼 챗봇
- 좋은 프롬프트보다 좋은 작업장이 먼저다
- 강한 에이전트의 문제는 대답이 아니라 권한이다

## 3-2. 한 장 요약 페이지
복잡한 주제를 한눈에 보여주는 페이지다.

### 예시
- Chat / Projects / Cowork / Claude Code 비교
- 자동화 가능 / 사람 검수 필요 구분
- CLAUDE.md / Skill / Subagent / Hook / MCP 구분

## 3-3. 비교 카드 페이지
잘못된 방식과 올바른 방식을 나란히 보여주는 페이지다.

### 예시
- 나쁜 요청 vs 좋은 요청
- 긴 프롬프트 vs 좋은 작업 구조
- 무턱대고 자동화 vs 검수선 있는 자동화

## 3-4. 실전 예시 페이지
한 직무나 상황을 기준으로 실제 문장을 보여주는 페이지다.

### 예시
- 개발자용 버그 수정 요청
- PM용 회의록 정리 요청
- 마케터용 카피 보정 요청

## 3-5. 실패 패턴 페이지
사람들이 실제로 자주 망하는 장면을 보여주는 페이지다.

### 예시
- 한 세션에 너무 많은 일 섞기
- 컨텍스트 과하게 넣기
- 검증 없이 결과만 믿기
- 비개발 업무를 안전하다고 착각하기

---

# 4. 타이포 원칙

## 제목
짧고 세게 쓴다.
가능하면 1~2줄 안에서 끝낸다.

### 좋은 예시
- Claude는 하나가 아니다
- 컨텍스트 관리가 실력이다
- 자동화는 사람을 없애는 기술이 아니다

### 피해야 할 예시
- Claude를 효과적으로 사용하기 위한 작업 구조 이해하기
- 컨텍스트 관리의 중요성에 대한 설명

## 본문
짧은 문단 위주로 간다.
한 문단은 2~4줄 정도가 적당하다.

## 강조문
굵게 너무 많이 쓰지 않는다.
정말 남겨야 할 문장만 살린다.

---

# 5. 컬러 방향

기본은 어두운 톤이나 차분한 밝은 톤 둘 다 가능하다.
중요한 건 색이 많지 않아야 한다.

## 추천 방향 A: 다크 프리미엄
- 배경: 거의 검정
- 본문: 부드러운 회색/오프화이트
- 포인트: 골드 또는 차가운 블루 1개

## 추천 방향 B: 라이트 에디토리얼
- 배경: 따뜻한 화이트
- 본문: 진한 차콜
- 포인트: 딥 블루 또는 포레스트 그린 1개

## 원칙
- 포인트 컬러는 1~2개만
- 경고/위험/좋음 정도만 보조색 사용
- 색으로 다 설명하지 말고 구조로 먼저 설명

---

# 6. 카드 시스템

## 6-1. Do / Don’t 카드
두 개를 나란히 놓고 비교한다.

### 쓰기 좋은 곳
- 좋은 요청 / 나쁜 요청
- 좋은 자동화 / 위험한 자동화
- 좋은 폴더 구조 / 나쁜 폴더 구조

## 6-2. Signal 카드
독자가 꼭 기억해야 할 한 줄을 카드로 뽑는다.

### 예시
- 좋은 결과는 긴 프롬프트보다 좋은 작업 구조에서 나온다
- 컨텍스트는 많다고 좋은 게 아니다
- 자동화의 핵심은 사람을 없애는 게 아니다

## 6-3. Warning 카드
실패 패턴이나 보안 위험을 짧게 경고한다.

### 예시
- 외부 자료를 읽힌다고 해서 다 믿으면 안 된다
- 되돌리기 어려운 작업은 사람 검수 없이 넘기지 말 것

---

# 7. 표 시스템

이 가이드의 핵심 문법은 표다.
표는 길게 만들지 말고, 판단 기준이 바로 보이게 해야 한다.

## 좋은 표의 조건
- 열이 너무 많지 않다
- 한 칸에 문장이 너무 길지 않다
- 읽는 순간 차이가 보인다
- 실제 선택에 도움이 된다

## 자주 쓸 표 종류
- 도구 비교표
- 역할별 추천표
- 자동화 가능 범위표
- 실패 원인 / 해결 방식 표

---

# 8. 시각 흐름

페이지를 넘길 때 리듬이 있어야 한다.
추천 흐름은 아래 같다.

1. 강한 선언
2. 한 장 요약
3. 비교표
4. 실전 예시
5. 실패 패턴
6. 한 줄 정리

이렇게 가면 독자가 덜 지치고,
읽다가 중간에 캡처해가기도 좋다.

---

# 9. 문장과 디자인의 관계

이 문서는 디자인이 문장을 살려야 한다.
문장이 약한데 디자인만 세면 공허해 보인다.
반대로 문장이 센데 디자인이 답답하면 힘이 죽는다.

그래서 원칙은 하나다.

> 강한 문장은 크게 보여주고, 설명은 짧게 붙이고, 판단 기준은 표로 빼라.

---

# 10. 최종 느낌

이 가이드를 봤을 때 독자가 느껴야 하는 건 아래 셋이다.

1. 생각보다 쉽다
2. 생각보다 실전적이다
3. 저장해두고 다시 보고 싶다

그 느낌이 나오면 성공이다.
