# 2. Recommended Structure

## Part 1 — Understand Claude in 5 Minutes

### 2.1 The fastest explanation

Claude has multiple work surfaces.
They are not the same tool with different skins.
They support different types of work.

| Surface | Best for | Weak at | Best user type |
|---|---|---|---|
| Claude Chat | quick thinking, summarizing, drafting | persistent operational workflows | everyone |
| Projects | keeping shared background context | active execution | researchers, PMs, founders |
| Cowork | file-based knowledge work | deep code changes | non-developers, operators |
| Claude Code | implementation, testing, refactoring | broad document delegation | developers |

### 2.2 One-sentence mental model

- **Chat** = ask and think
- **Projects** = keep context
- **Cowork** = delegate document work
- **Claude Code** = implement and verify

### 2.3 Common misunderstanding

**Wrong:** “Claude is one product, so all surfaces should feel similar.”

**Right:** “Same intelligence, different workbench.”

## Part 2 — The Beginner Playbook

### 2.4 Good first tasks vs bad first tasks

#### Good first tasks
- summarize a report into 5 bullets and 3 questions
- convert meeting notes into a weekly brief
- ask Claude Code to make a fix plan before editing code
- organize reference material into a reusable template

#### Bad first tasks
- connect every plugin and external tool on day one
- ask for full product implementation without scope boundaries
- automate outbound communication without approval steps
- say “do everything in our tone” without examples or templates

### 2.5 Bad request vs good request

#### Example A — Bug fix

**Bad**  
Fix the login bug.

**Better**  
Read only the auth-related files, do not touch env settings, identify the likely cause first, then implement the smallest safe fix and report what changed.

#### Example B — Weekly brief

**Bad**  
Make a market update.

**Better**  
Read these notes and links, summarize only what changed this week, explain why it matters to us, and end with 3 action items.

### 2.6 Why beginners fail

Beginners usually fail for one of these reasons:

1. they pick the wrong surface
2. they ask too broadly
3. they do not separate context, templates, and outputs
4. they expect automation before designing guardrails
5. they confuse “smart answer” with “reliable workflow”

## Part 3 — Comparison-Driven Understanding

### 2.7 Chat vs Cowork vs Claude Code

| Situation | Chat | Cowork | Claude Code |
|---|---|---|---|
| brainstorming | best | okay | overkill |
| turning notes into docs | okay | best | inefficient |
| recurring report generation | okay | best | usually overkill |
| code bug fixing | weak | poor fit | best |
| test and verification | weak | poor fit | best |
| folder-based knowledge workflows | limited | best | mixed |

### 2.8 Skill vs Plugin vs MCP

| Term | What it really means | Easy explanation |
|---|---|---|
| Skill | repeatable procedure | “how to do this well” |
| Plugin | packaged work setup | “installable role box” |
| MCP | external tool connection layer | “how Claude reaches outside systems” |

### 2.9 Automation vs human review

| Task type | Can automate? | Human review required? |
|---|---|---|
| first draft writing | yes | yes |
| summarization | yes | recommended |
| internal brief generation | yes | recommended |
| code change | yes, with guardrails | yes |
| external sending | partially | mandatory |
| deletion / payment / irreversible action | no full autonomy | mandatory |

## Part 4 — Tone & Manner System

### 2.10 Tone principles

A premium guide should sound:

- sharp, not noisy
- easy, not dumbed down
- practical, not academic
- confident, not hypey
- friendly, not childish

### 2.11 Recommended tone examples

#### Strong headline style
- Claude is not a chatbot. It is a work system.
- The problem is rarely the model. It is usually the setup.
- Don’t automate everything. Automate what repeats.
- Better outputs start with better work boundaries.

#### Explainer style
- Use short paragraphs.
- Prefer contrast over abstraction.
- Teach through choices, not lectures.
- End sections with action-oriented summaries.

### 2.12 Comparison box pattern

Every major concept should be explained with:

1. what it is
2. what it is not
3. when to use it
4. when not to use it
5. a quick before/after example

## Part 5 — Structure for Easy Understanding

### 2.13 The ideal folder structure

```text
workspace/
├── context/
│   ├── about.md
│   ├── rules.md
│   └── glossary.md
├── projects/
│   └── current-project/
│       ├── brief.md
│       └── source-materials/
├── templates/
│   ├── weekly-brief-template.md
│   └── meeting-summary-template.md
├── outputs/
└── handoff/
```

### 2.14 Why this structure works

- context = things Claude should repeatedly know
- projects = active work materials
- templates = output standards
- outputs = generated results
- handoff = continuity for future sessions or teammates

### 2.15 Bad structure vs good structure

#### Bad
Everything mixed in one folder with vague filenames like final-final-v2.md.

#### Good
Clear separation between source materials, templates, outputs, and handoff notes.

## Part 8 — The Review Loop

This guide should not be written in one pass.

Check:
- Is the order intuitive?
- Does each section earn its place?
- Does the reader know what to do next?

### Loop 2 — Beginner clarity review
Check:

- Are jargon-heavy areas converted into comparisons or examples?
- Is every concept grounded in a real use case?

### Loop 3 — Tone review
Check:
- Does it sound premium and clear?
- Are headlines memorable?
- Is any section verbose or repetitive?

### Loop 4 — Design review
Check:
- Which pages deserve diagrams?
- Which paragraphs should become cards, tables, or callouts?
- Where can visual pacing improve comprehension?

### Loop 5 — Practicality review
Check:
- Can the reader use this immediately?
- Are there enough examples to copy?
- Does the guide reduce ambiguity?
